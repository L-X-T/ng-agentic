Owning the Review

Agents made writing code cheap; reviewing it is now where quality is decided. You'll review one real diff three ways – machines first, then an independent agent reviewer, then your own judgment on its findings – and practice the step you never delegate: the final call.

Angular v22 Focus Reviewing Est. time ~30 min Level all levels Builds on Labs 00–03

About this lab

Lab 03 was about opening the loop well; this lab closes it. You'll take one real diff, gate it through the feedback loops, run the code-review skill for an independent second opinion, then act on the findings without rubber-stamping them. The full guide is 04-REVIEWING.md.

Every workflow ends with review including the commit – the agent prepares the diff, the human owns the judgment. When code ships in minutes, a repeatable review process is what keeps agentic speed from shipping regressions.

Learning objectives

  • Gate a diff through the feedback loops (build, lint, format, test) before spending human attention.
  • Pick one explicit review scope and run two passes: correctness, then style-guide conformance.
  • Dispatch an independent agent reviewer with the code-review skill.
  • Verify findings before acting, fix by severity, and push back on false positives with evidence.

Prerequisites

  • Finished Lab 00 and Lab 01 – a project of your own with the feedback loops running.
  • Finished Lab 02. Copy code-review from the workshop clone into your local skills folder and confirm your agent discovers it.
  • A diff to review: work in progress, or your Lab 03 result. No diff? Use the prepared booking-filter review with known defects and a facilitator key.

Steps

  1. Machines first, then pick your scope
  2. Run an independent agent review
  3. Verify findings, act by severity, close the loop

1 Machines first, then pick your scope

Goal: spend zero human attention on problems the tools find for free, and make the review target explicit.

Run the feedback loops from your Lab 01 setup – the build → lint → format → test chain Lab 07 will name the gauntlet. Read the verification contract. Repair new failures, recheck the final files and record intentional baseline debt. Tool silence alone does not prove the requirement. Then pick exactly one scope from 04-REVIEWING.md: current work, staged work, last commit, or a merge/PR range. If your own project has no test script or a pre-existing red baseline, note that and gate on the checks your project actually has.

On the prepared case there is nothing to build: record that the fixtures were not compiled or browser-tested, and use its git diff --no-index command as your scope, reading the new template as a plain file.

Your task

  1. Run the loops: build, lint, format, test.
  2. Investigate failures, record intentional baseline diagnostics, and repair new failures within scope. Re-run checks on the final files.
  3. Choose your scope and write down the exact git commands that show it (prepared case: the --no-index diff plus the template file).
  4. Read the raw diff once yourself, uninterrupted, before any agent opinion touches it.
Show solution – gating and scoping 
shell# the feedback loops – adjust to your project's scripts
pnpm workshop:check

# scope: current work
git status --short
git diff --stat
git diff

# scope: prepared case – no loops to run, the fixtures live outside the app
git diff --no-index labs/cases/review/before.ts.txt labs/cases/review/after.ts.txt
cat labs/cases/review/after.html.txt

Reading the diff yourself first anchors your judgment before the reviewer's framing arrives. You'll disagree better in Step 3 for it.

Checkpoint: checks pass or match the recorded exercise baseline (or you've recorded that the prepared fixtures were not compiled), you've named one scope with its exact git commands, and you've read the raw diff once yourself.

2 Run an independent agent review

Goal: get a second opinion from a reviewer that did not write the code – fresh context, read-only, two passes.

Invoke the code-review skill. It gathers a handoff (description, requirements, verification state, scope, diff commands), dispatches a read-only reviewer subagent, and returns findings ranked Critical / Important / Minor across two passes: correctness against the requirements, then style-guide conformance for every touched file type.

Your task

  1. Confirm code-review is available – copy it from the workshop clone if it is not installed yet.
  2. Invoke it on your chosen scope and let it drive the handoff and dispatch. On the prepared case, hand it the contract from requirements.md and the three fixture paths, and say the fixtures were not compiled.
  3. While it runs, list your own top three concerns from your Step 1 read.
  4. Compare: what did it find that you missed – and what did you catch that it didn't?
Show solution – invoking the review 
textRun the code-review skill on my current work: I added a status filter
to the bookings table. Requirements: hide cancelled bookings, keep the
BookingService API and sorting behavior unchanged.
Verification: pnpm lint and pnpm test are green.

Naming the requirements is what powers the correctness pass – without them the reviewer can only judge style. A decision list from your Lab 03 grilling session is exactly the requirements input a reviewer needs.

Checkpoint: you have a findings list ranked by severity, plus your own three concerns to hold it against.

3 Verify findings, act by severity, close the loop

Goal: turn the findings list into judgment – confirm, fix, defer, or push back – and finish with a commit you own, or, on the prepared case, a written disposition for every finding.

Findings are claims, not facts. For each: open the file, read the line, reproduce the problem. Fix valid Critical issues immediately and valid Important ones before proceeding; note Minor ones for later. Reject wrong findings with file/line evidence or test output – agent reviewers are confident false-positive machines, and accepting a wrong finding damages the code as surely as missing a real one.

Your task

  1. Verify every finding against the code before touching anything.
  2. Fix the valid Critical and Important findings (let the agent do the edits – you judge them). On the prepared case, do not edit the fixtures: record the fix you would make instead.
  3. Push back on at least one finding you can refute with evidence – or document why all held up.
  4. Re-run the loops, re-review the fixed portion, and commit the result yourself. The prepared case has nothing to commit: compare your dispositions with the facilitator key instead.
Show solution – pushing back with evidence 
textFinding 2 claims the filter breaks for undefined status. That path
can't occur: BookingStatus is a required union type, and the mapper
in booking.mapper.ts:34 defaults unknown values to "unknown".
Rejecting this one – show me a failing input if you disagree.

Note the shape: a concrete counter-reason plus an invitation to prove otherwise. If the reviewer produces a failing input, confirm the defect and assess severity from its impact.

Checkpoint: every finding is fixed, deferred, or rejected with evidence; checks pass or match the recorded exercise baseline; and you made the commit – or, on the prepared case, every finding has a written disposition that you compared with the facilitator key.

Review evidence

Record every disposition

For each finding, record requirement, file/line, reproduction, impact and disposition. For the prepared case, compare your result with its facilitator key only after reviewing. Count confirmed defects, misses and false positives. A credible uncertain finding can ask for a missing check; it must not claim an unexecuted test passed.

Live completion for the text fixture means a scoped review and evidence-based dispositions. There is no implementation to commit in that path. For your own project, finish with the final verified diff and your reviewed commit.

Definition of Done

You've completed Lab 04 when…

  • ✅ You recorded check results and requirement-specific evidence before reviewing the diff.
  • ✅ You reviewed against an explicit scope with named git commands.
  • ✅ An independent agent review ran via the code-review skill, two passes, ranked findings.
  • ✅ You verified every finding before acting and fixed by severity.
  • ✅ You pushed back on a finding with evidence – or confirmed they all held.
  • ✅ You reviewed the final diff before committing your own project, or completed evidence-based dispositions for the prepared text fixture.
