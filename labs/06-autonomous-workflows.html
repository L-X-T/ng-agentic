Running Autonomous Workflows

Lab 05 kept you at every checkpoint. This lab flips the mode: you hand the agent a verifiable goal and the guardrails, walk away, and come back to review finished work. You'll climb the autonomy ladder – a goal-driven run, then a loop or an orchestrator – plus a bonus look at agents that run 24/7 without your laptop.

Focus Autonomous workflows Builds on Labs 00–05 Est. time ~30 min Bonus always-on agent

About this lab

This is Lab 06. In Lab 05 you gated every step yourself. Autonomous workflows replace those human gates with checks the agent runs on its own – a passing suite, a green build, a clean lint. The full guide is 06-AUTONOMOUS-WORKFLOWS.md.

The invariant is not waived, only deferred: every run still ends with your review and your sign-off – your commit, or your merge of the run's working branch – against the accumulated diff instead of at each step. Treat the output as a draft for Lab 04's reviewing practice, never as approved work.

This is a guided ~30 min run; assignment 1 – the goal-driven run – is the priority. One of assignments 2 / 3 is required but fine to finish as homework if time runs out; the bonus is optional.

The contract

Autonomous work only converges when three things hold: a verifiable goal the agent can check itself, a feedback signal inside the run (the checks after each iteration), and guardrails so a wrong turn stays contained. If one is missing, stay in the loop – Lab 05's workflows are the right mode for unverifiable work.

The autonomy ladder

Learning objectives

  • Turn a task into a verifiable goal statement: definition of done, feedback checks, scope, guardrails.
  • Run a goal-driven session unattended and review the accumulated diff afterwards.
  • Set up a recurring loop or an orchestrator that fans work out and verifies results.
  • Know what it takes – and what it risks – to run an agent 24/7 on its own machine, in CI, or as a PR review bot, and how to harden the harness for unattended runs.

Prerequisites

  • Finished Lab 00–Lab 05 – your project is agent-ready and you know the human gates before you remove them.
  • A task with real checks: a test suite, lint, or build that can tell the agent it is done.
  • A clean Git working tree, and a branch or worktree the agent can safely own.
Guardrails before you leave

Before every unattended run: put the agent on its own branch or worktree, deny push and destructive commands, keep production credentials out of reach, and scope the task so a wrong turn stays contained. The agent must not be able to do irreversible damage while you are away.

Prepared cases

Fallback path: repair, then stop at a blocker

Use the prepared autonomy cases when your project has no suitable failing test. They include a real red, a solvable repair, a missing-rule blocker and harmless instruction/enforcement probes. On this path, assignment 1 is Case 1 (a bounded repair verified by node --test) followed by Case 2 (a correct blocker report). Case 3 and scheduled or orchestrated runs on the cases are optional extras.

Before any run, record the five dimensions from the chapter – authority, trigger, workers, hosting and limits – and confirm in the capability check which goal and scheduling commands your installed harness actually offers rather than assuming a slash command exists.

1 Goal-driven run

Goal: hand the agent one bounded task with a verifiable definition of done, and be elsewhere while it finishes.

Pick a task a machine can verify: make a failing test pass, drive a lint rule to zero, raise coverage on one module, or fix a bug that has a regression test. No such task in your project right now? Create a real red before the run: add a focused regression test for missing behavior, or introduce a disposable production defect on a throwaway branch that makes a passing test fail, then watch the check fail. Commenting out or weakening a passing test is not a red signal. Write the goal statement as carefully as a Lab 03 prompt – it carries everything you would normally say at the checkpoints.

Your task

  1. Write a goal statement: definition of done, the checks to run each iteration, and the files in scope.
  2. Put the agent on its own branch or worktree and allow the check commands up front: a goal does not change the permission mode, so in Claude Code run it in auto mode or pre-allow the build, lint and test commands in your settings, or the run blocks on the first permission prompt while you are away.
  3. Start the run with the goal command your capability check confirmed (/goal in current Claude Code and Codex CLI builds) and walk away – no steering.
  4. When it stops, review the accumulated diff Lab 04 style: machines first, one scope, two passes – then commit it yourself.
Show example goal 
prompt/goal Fix orderTotal in labs/cases/autonomy/order-total.mjs without editing its test.

Definition of done: `node --test labs/cases/autonomy/order-total.test.mjs` passes all three tests.
After each change, re-run that command and iterate on the failures.
Scope: that one file only; tests, scripts and configuration are read-only.
Do not delete, skip, or weaken tests to make the check pass.
Stay on this branch; never stage, commit, or push; never delete files outside the scope.
Stop after 10 minutes or 3 failed repairs.
On a blocker, preserve the diff and report the missing information instead of guessing.

In your own project, swap in your failing check (for example pnpm test --watch=false) and the files in scope. If the run drifts or stalls, that is a finding, not a failure: tighten the goal or the scope and run it again. A run is only as good as its definition of done.

Checkpoint: the agent reached the verifiable goal without you, and you reviewed the accumulated diff and made the commit.

2 Recurring loop · pick one of 2 / 3

Goal: set up a loop that re-runs a small check on an interval while your attention is elsewhere.

Loops fit work whose trigger is time or an external event: watch CI, check whether a deploy landed, babysit an open PR, re-run a flaky suite until it fails and capture the evidence. Pick one that is real right now.

Your task

  1. Choose a condition worth watching and an interval – frequent enough to be useful, rare enough not to spam.
  2. Start the loop using your installed harness: /loop in Claude Code, or a scheduled task created from a Codex chat in the desktop app (the Codex CLI has no loop command), with a prompt saying what to check and what to do on each outcome.
  3. Let it run two or three iterations while you do something else, then review what it did and cancel it yourself: a fixed-interval loop runs until you cancel it or seven days pass, so confirm it is gone from the scheduled task list.
Show example loop 
prompt/loop 10m Check the CI status of the current branch.
If still running or unchanged, stay quiet. Report a meaningful success or failure once.
If it failed, read the failing job's log, identify the cause, and propose
a fix as a diff – but do not apply it until I approve.
Stop reporting after two checks or 20 minutes.

Note the asymmetry: the loop may observe autonomously, but the fix still waits for you. Widen its permissions only when the repair itself is machine-verifiable. The loop cannot end itself: cancel the task when you are done.

Checkpoint: the loop ran unattended for several iterations, its reports were useful, and you reviewed everything it produced.

3 Orchestrator · pick one of 2 / 3

Goal: decompose one goal across several subagents and merge only verified results.

Pick a job that genuinely decomposes: a review of assignment 1's diff from three lenses (correctness, security, performance), a mechanical migration across many files, or research that fans out over sources. The orchestrator plans and synthesizes; the subagents do the parallel work in fresh contexts.

Your task

  1. Ask the lead to decompose the goal into independent work items and show you the split before it fans out.
  2. Let it spawn one subagent per item – parallel reviewers with different lenses, or one implementer per worktree.
  3. Require verification before synthesis: findings are checked (ideally by an adversarial subagent) before they reach the summary you review.
Show example prompt 
promptReview the diff of my last commit with three parallel subagents,
one lens each: correctness against the spec, security, performance.
Then have a fourth subagent try to refute each finding.
Report only the findings that survive, ranked by severity –
I will decide what gets fixed.

Orchestration buys wall-clock speed and independent verification, and costs tokens and review volume. If the job does not decompose, one agent on one branch is simpler and usually faster.

Checkpoint: the work was split, executed in parallel, and verified before synthesis – and you reviewed the merged result, not the raw fan-out.

4 Bonus – an agent that never sleeps

Goal: design (or build) an always-on agent setup that works without you or your laptop.

Local execution depends on its session or scheduler and host staying available. The top of the ladder is an agent on a dedicated machine – the classic is a Mac mini in a closet, but any small server or VPS works – running 24/7 with OpenClaw (a personal assistant gateway with messaging and scheduled tasks) or Hermes Agent (self-hosted, persistent memory, recurring tasks). CI schedules give the same property without the hardware.

Your task

  1. Pick one standing duty: nightly dependency triage, a morning issue summary, babysitting long jobs, a scheduled refactoring sweep.
  2. Write the runbook: which machine or service, which system (OpenClaw, Hermes, a CI schedule), which schedule, and how results reach you.
  3. Harden it on paper: dedicated accounts, scoped credentials, no production secrets, a spend cap, an audit trail. If you have spare hardware – set it up for real.
Alternative: put the agent in CI instead

Instead of the always-on runbook, set up – or design on paper – a CI agent workflow or a PR review bot for your own repository: an issue-triggered implementation job, a nightly maintenance run, or an independent review on every PR (see Agents in CI and PR review bots in the guide). Apply the guardrails from Hardening the harness: scoped credentials and permissions, no secret reads, untrusted content treated as data, and a human on the merge button – bots comment, humans merge.

Standing autonomy is standing risk

An always-on agent is an employee you never watch – onboard it like one. Everything it commits still lands in front of a human before it merges; 24/7 execution does not mean 24/7 approval.

Checkpoint: you have a concrete, hardened runbook for one always-on duty – or a spare machine actually running it – or a hardened CI agent / review bot design for your own repository.

Definition of Done

You've completed Lab 06 when…

  • ✅ One goal-driven run finished a verifiable task unattended – in your project, or Case 1 of the prepared cases – and you reviewed the result and, in your own project, committed it.
  • ✅ If you used the prepared cases: Case 2 stopped with an evidence-backed blocker report and the protected files are unchanged.
  • ✅ One of assignments 2 / 3 – a bounded loop or an orchestrated review – produced verified results, in class or as homework, and any schedule you created is cancelled.
  • ✅ You can name the three parts of the contract – verifiable goal, feedback signal, guardrails – and what happens when one is missing.
  • ✅ Bonus: you designed (or built) an always-on agent setup – or a CI agent / PR review bot for your own repository – with hardened credentials and an audit trail.
