Working with Agent Skills

A skill is a folder of instructions your agent loads on demand and follows the same way every time. In this lab you'll put a couple of this repo's skills to work on your own project, then author one of your own.

Angular v22 Focus Agent Skills Est. time ~30 min Level intermediate Builds on Labs 00–01

About this lab

A skill lives under .agents/skills/ as a SKILL.md – the instructions the agent follows. The agent keeps each skill's name and description in view and loads the full body only when your request matches. Browse the catalogue in 02-SKILLS.md.

Two parts: use a skill or two from this repo on the project you brought (Lab 00), then build one of your own with the create-a-skill meta-skill. A good prompt helps once; a good skill helps every time.

Learning objectives

  • Read a skill's frontmatter and body to judge whether it fits a task.
  • Make skills available to your agent – personal or project folder – and invoke them.
  • Tell when a defined process beats an ad-hoc prompt.
  • Author a new skill – frontmatter, a triggering description, and a tight body.

Prerequisites

  • Finished Lab 00 – a small project of your own and a written goal.
  • Finished Lab 01 – agentic tooling and an AI coding agent working.
  • This ng-agentic repo checked out, so you can copy its skills from .agents/skills/.
How to work through this lab

Each step has a Goal, a Your task box, an optional collapsible Solution, and a Checkpoint. Both parts are open-ended – there's no single right answer.

Part 1 – Use a skill on your project

1 Choose and install the skills you need

Goal: install the workshop-required skills locally, then choose one or two task skills to test on a real task.

A skill is a folder of executable instructions, and some in this catalogue deliberately depend on this workspace's style guides, scripts, and packages. Keep the workshop set local to your project rather than exporting every assumption to unrelated projects. Open 02-SKILLS.md, skim the catalogue, and match one or two task skills to the goal you wrote in Lab 00.

Your task

  • Copy create-a-skill into your project’s .agents/skills/ folder; install other process skills when their exercise needs them.
  • Pick and copy one or two task skills that fit your project – you'll run those next.
  • Restart your agent so it discovers the newly installed local skills.

Local installation keeps the workshop's assumptions attached to the project they were written for. Before promoting any skill to ~/.claude/skills/ or ~/.agents/skills/, inspect its references, scripts, commands, package assumptions, and safety rules; make only genuinely portable skills global.

Where skills live: local vs global

Always distinguish local from global skills. Local (project/workspace) skills are committed to the repo – this workspace stores them in .agents/skills/. Verify discovery in your actual harness; see the capability and evaluation guide. Global (user) skills travel with you across projects and are copied into each agent's home: ~/.claude/skills/ for Claude Code and ~/.agents/skills/ for Codex. Commit team-shared and repository-specific skills to the project; reserve global installation for reviewed, portable personal workflows. If a skill doesn't trigger, check it's in a directory your agent actually scans, and restart.

Checkpoint: the required local skills and your one or two task picks are installed, and your agent lists them.

2 Run it and compare

Goal: invoke each skill on its task and notice how a defined process changes the result. Skills like accessibility audits and e2e tests act as repeatable quality gates – the same checks, the same way, every time.

Trigger a skill by describing the task in its own words – the matching description is what makes it fire. Then look at how it worked, not just what it produced.

Your task

  1. Invoke each skill on the task you picked for it; let it drive its own process.
  2. For each, note one thing it did that you'd have forgotten to ask for.
Show solution – triggering a skill

Describe the job the way the skill advertises it, one request at a time:

textBuild a booking-list component following the project conventions.
Now make that component accessible and pass an axe audit.

Each request matches a different skill's description, so the right process kicks in.

Tip – read the body alongside the run

Open the skill's SKILL.md while you review the transcript. Seeing the instructions next to the behaviour is the fastest way to learn what makes a skill effective – ammunition for Part 2.

Checkpoint: a skill ran on your project, and you can name what its process gave you over a bare prompt.

+ Bonus – read a skill against your project rules

Goal: a well-written skill can still misbehave because it disagrees with the host project's rules. Find that disagreement before the agent does.

Skills carry their author's assumptions: package manager, test runner flags, whether the agent may start a dev server, what Git commands it may run. Your project's AGENTS.md (or equivalent) owns those decisions, and a copied skill only helps if the two agree.

Your task

  • Open one skill you copied in step 1 and read it next to your project's instruction file.
  • List every place the skill contradicts your rules – commands, file paths, servers, Git, wording.
  • Fix the copy locally (detection over assertion: "check for X; if present…") and note what changed.
Tip – the usual suspects

npm/npx versus your package manager, test commands that enter watch mode, an unguarded ng serve, hard-coded repo files that don't exist in your project, and Git commands the skill runs on its own initiative.

Checkpoint: one skill is reconciled with your project rules and you can name the assumptions it carried.

Part 2 – Build your own skill

3 Find a process and author the skill

Goal: pick a task you do repeatedly and turn it into a working SKILL.md using the create-a-skill meta-skill.

The best first skill is small and real: a chore you've explained to an agent more than once, or a team convention you keep restating. Let the repo's own create-a-skill skill scaffold it – it knows about triggering descriptions, leading words, and keeping the body to steps that earn their place.

Your task

  1. Name the trigger (becomes the description), the ordered process, and the done condition.
  2. Decide the scope: a local (project) skill goes into your repo's .agents/skills/<your-skill>/, a global (user) skill into the supported personal directory for your chosen host, such as ~/.claude/skills/ and ~/.agents/skills/. Then invoke create-a-skill to scaffold it there.
  3. Write a description naming the words you'd actually say; write the body as numbered steps, each ending in a "done" condition.
Show solution – a minimal SKILL.md skeleton 
markdown---
name: draft-commit-message
description: Write a Conventional Commits message for the staged changes, following the
  repo's git style guide. Use when the user asks to draft a commit message or format a
  commit subject/body. This skill proposes text; it does not stage, commit, or push.
license: MIT
metadata:
  author: Your Name
  version: '1.0'
---

# Draft a commit message

Turn the staged diff into one Conventional Commits message.

## Process

### 1. Read the staged changes
Run `git diff --staged`. If nothing is staged, stop and say so.

### 2. Classify
Pick the type (feat, fix, docs, refactor, test, chore) and an optional scope from the paths touched.

### 3. Write the message
Imperative subject under 72 chars; add a body only if the "why" isn't obvious. Never invent
changes that aren't in the diff.

_Done when_ a valid `type(scope): subject` message is proposed for the user to commit.

A complete skill – body only, no bundled files. Add a reference file (e.g. references/examples.md) only when the body would otherwise bloat.

Tip – the description is the most important line

A skill only helps if it triggers. Front-load the description with the words a user would actually use, and say when not to use it. Vague descriptions are why skills sit unused.

Checkpoint: a SKILL.md exists in your agent's skills directory with valid frontmatter and a numbered body.

4 Make it trigger (Bonus: document it)

Goal: confirm the skill fires on a natural request and refine it until it does.

Your task

  1. Start a fresh agent session and make a request in your own words – does the skill trigger?
  2. If it doesn't, sharpen the description's leading words and try again.
  3. Bonus (local skills): run update-skills-directory to validate the SKILL.md and link it from your repo's skills index – in this workspace that's 02-SKILLS.md; if your own project has no index yet, ask the skill to create a minimal one first.
Show solution – verify & index

Test triggering by describing the task, not by naming the skill:

textDraft a Conventional Commits message for my staged changes.

Bonus – keep the docs honest:

textUse the update-skills-directory skill to validate and index my new skill.

It audits the repo's .agents/skills/, checks the structure, then links your skill into the repo's 02-SKILLS.md – so it only sees local (project) skills, not global ones in ~/.claude/skills/ or ~/.agents/skills/.

Iterate – first drafts rarely trigger

If the agent ignores your skill, check the location first (the folder must be one your agent scans, and a restart is needed after adding it). After that, the description is almost always the culprit: add the exact phrases you'd say, and a "use when…" clause.

Checkpoint: a natural request triggers your skill.

Evaluate selection, process and boundaries

Use the five cases in the evaluation sheet: match, paraphrase, non-match, missing prerequisite and authority boundary. Record expected and actual selection, the steps taken and whether the output was useful. A draft-only request must not create a commit. Keep failed cases when revising your description.

Live checkpoint: one task skill ran and a new skill passed a match and a boundary case. Complete all five cases and the portability exercise after class. Before sharing globally, try a disposable project with different script names and conventions and record assumptions that had to change.

Definition of Done

You've completed Lab 02 when…

  • ✅ You ran a skill from this repo on your own project and saw it follow its process.
  • ✅ You can explain what a skill's process gave you over a plain prompt.
  • ✅ You authored a new skill for a repeatable process, with valid frontmatter and a numbered body.
  • ✅ A match follows the process and a boundary case stops appropriately; record selection and output evidence.
