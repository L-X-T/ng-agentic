From Prompt to Shared Understanding

The prompt is the highest-leverage artifact in agentic work: five sentences decide whether the next twenty minutes produce the change you wanted or a confident guess. Run the same task at three prompting levels – simple, interactive, and a full grilling session – and feel where each earns its keep. Then hand the work to a fresh session and check that the decisions survived.

Angular v22 Focus Prompting & Context Est. time ~30 min Level all levels Builds on Labs 00–02

About this lab

This is Lab 03. You chose a project in Lab 00, prepared it in Lab 01, and tried skills in Lab 02. Now you practice the craft everything builds on: telling the agent what you want. The three levels of 03-PROMPTING.md are the map – this lab is the territory.

Carry one task through all the prompting steps so the levels are directly comparable; the bonus handover step then carries the same work into a fresh session. The default task is the booking filter from the acceptance sheet, mapped onto a sortable list in your own project. If you would rather bring a task your project needs, write an equivalent sheet first – the sheet explains both options. Diagnose disappointing output against the prompt, discovered context, tools, checks and model; do not assume the cause.

Learning objectives

  • Write a prompt with the five parts: observation, goal, constraints, scope, and check.
  • Turn a one-shot prompt into an interactive one that makes the agent ask questions first.
  • Run a grilling session with grill-me or grill-with-style and capture its decisions.
  • Judge which prompting level a given task deserves – and when to escalate.
  • End a session with the handover skill and continue the work in a fresh one.

Prerequisites

  • Finished Lab 00 and Lab 01 – you have a project and a working agent.
  • Finished Lab 02. Copy the chosen grilling or brainstorming skill from the workshop clone if you use that bonus; copy handover for the session-transfer exercise.
  • A task with a fixed acceptance sheet: the booking filter mapped onto a list in your project (add a minimal list first if none fits), or your own task with a sheet written before the first run.
  • A saved baseline revision and a separate disposable worktree per run. Use the same code, harness/model settings and acceptance cases; preserve unrelated work.

Use the booking-filter acceptance and comparison sheet, or your own sheet built from it. All levels implement that same task. Record behavior, useful questions, review minutes and unrequested changes. Changed requirements make runs incomparable unless recorded explicitly.

Steps

  1. Write a simple prompt – all five parts
  2. Make the agent ask you questions
  3. Run a grilling session (Bonus)
  4. Hand the work to a fresh session (Bonus)

Definition of Done · Next lab

1 Write a simple prompt – all five parts

Goal: feel the gap between a vague prompt and a five-part prompt on the same task.

First write the prompt you would have typed before this workshop – one lazy sentence. Then rewrite it with the five parts from 03-PROMPTING.md: observation, goal, constraints, scope, check.

Your task

  1. Write the lazy version and save it in a scratch note.
  2. Rewrite it with all five parts, in your project's terms, naming real paths and a runnable check.
  3. Run the five-part version in a fresh agent session and review the diff.
  4. Compare: which decisions did the lazy version leave to the agent?
Show solution – a five-part prompt 
textLazy:    "Add filtering to the bookings table."

Better:  The bookings table shows cancelled bookings mixed in with active
         ones (observation). Add a status filter above the table so users
         can hide cancelled bookings (goal). Don't change the
         BookingService API or the existing sorting (constraints).
         Work only in the agreed booking component (scope). Done when cases A1–A6
         on the acceptance sheet pass and static checks show no new failures (check).

Count the open questions in the lazy version: which filter control? where? does it persist? may the service change? The agent would have had to answer every one alone.

Tip – the check is the part people skip

"Done when the acceptance cases and relevant checks pass" makes the requested behavior verifiable and gives the agent a feedback loop it can run without you. If you learn one habit here, make it this one.

Checkpoint: you have both prompt versions side by side and can name at least three decisions the lazy version silently delegated to the agent.

2 Make the agent ask you questions

Goal: run the same task interactively – the agent plans and interviews you before writing code.

Now assume you couldn't state the constraints confidently. Instead of guessing, run it in two beats: (1) plan and ask clarifying questions, then (2) implement. The two magic phrases are "before you write any code" and "one at a time".

Your task

  1. Start a fresh session and give the agent your task without the constraints and scope.
  2. Ask it to propose a short plan and ask clarifying questions, one at a time, before any code.
  3. Answer honestly. Stop the interview when a question no longer changes the plan.
  4. Let it implement, and compare the diff with Step 1's.
Show solution – the interactive prompt 
textI want to add a status filter to the booking table.
Before you write any code: propose a short plan and ask me
clarifying questions, one at a time, until the scope is unambiguous.
Then implement the plan we agreed on.

Notice what the questions surface: initial selection, sort order, empty results and keyboard interaction. Record which answers changed the implementation plan.

One at a time is not optional

If the agent dumps eight questions at once, you'll skim and half-answer them – and the half-answers become the spec. Insist on one question per turn; each answer should sharpen the next.

Checkpoint: the agent asked questions you hadn't considered, and at least one answer changed the plan before any code existed.

3 Run a grilling session · Bonus

Goal: escalate to Level 3 – a skill-driven session that stress-tests a plan until you and the agent share one understanding, written down.

Bring a plan with real design choices. Then pick your interrogator: grill-me for a relentless general grilling, or grill-with-style to ground every question in your project's style guide and domain language. If you only have an idea, not a plan, use brainstorming instead – it designs first and refuses to implement before you approve.

Your task

  1. Write your plan in three to five sentences.
  2. Invoke a grilling skill on it (or brainstorming) and let it walk the decision tree, one question at a time.
  3. For each question, note the agent's recommended answer – accept it or override it consciously.
  4. End by asking for a summary of every decision, and save it next to your project notes.
Show solution – starting the session 
textHere's my plan: a local All/Active filter hides cancelled bookings.
All restores the original data, the chosen sort still applies, and an empty
result says "No active bookings". No persistence or service API changes.

Grill me on this plan.

The phrase "grill me" selects the skill. Ask whether All includes unknown future statuses, whether the filter resets on reload, and how the existing sort composes with filtering. Record the agreed answers against the acceptance sheet.

Checkpoint: you have a written decision list from the session, and at least one decision differs from what you'd assumed going in.

4 Hand the work to a fresh session · Bonus

Goal: end a session with a written handover and verify a fresh session continues the work without losing a decision.

Long sessions can accumulate irrelevant context. If the agent loses decisions or repeats dead ends, create a reviewed handover. This repo ships the handover skill for exactly that: it compacts the conversation into a document the next session can start from.

Your task

  1. In the session from Step 2 or 3, invoke the handover skill and tell it what the next session will work on.
  2. Read the generated document: does it capture the decisions, or just the events? Fix gaps before moving on.
  3. Start a fresh session, point it at the handover doc, and give it a five-part prompt for the next slice of work.
  4. Verify the pickup: the new session knows the decisions and does not re-ask questions you already answered.
Show solution – handover and pickup 
textEnd of the old session:
  Handover – the next session will implement the status filter
  we just agreed on, against cases A1–A6.

Start of the fresh session:
  Read <the path the handover skill printed> first. The plan there is agreed
  (observation). Implement the status filter on the bookings
  table (goal). Preserve agreed decisions; flag contradictory repository evidence
  before changing them (constraints). Work in src/app/bookings/
  (scope). Done when A1–A6 and the relevant checks pass (check).

The new session should preserve All/Active semantics, sorting and the no-persistence decision. If code contradicts the handover, it should name the evidence and ask how to proceed before revising the contract.

Why not just keep the old session?

Because the context window is a budget – see Managing Context and Sessions. A fresh session with a five-part prompt plus a handover doc drops the sludge and keeps what the doc recorded – but a handover is lossy, like compaction. Verify the recorded decisions against the current code and next task.

Checkpoint: a fresh session continued the work from the handover doc alone – it preserved the decisions and surfaced any contradictory repository evidence before proposing a change.

Definition of Done

You've completed Lab 03 when…

  • ✅ You wrote a five-part prompt (observation, goal, constraints, scope, check) for a task with a fixed acceptance sheet.
  • ✅ You can name the decisions your old lazy prompt left to the agent.
  • ✅ You ran an interactive prompt and an answer changed the plan before any code existed.
  • ✅ (Bonus) You ran a grilling or brainstorming session and saved its decision list.
  • ✅ (Bonus) A fresh session continued your work from a handover document without re-asking settled questions.
