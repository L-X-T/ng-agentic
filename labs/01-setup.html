Hands-on Lab · Agentic Engineering

Set up an Angular project for Agentic Engineering

Reproduce the ng-agentic workspace conventions in your Lab 00 project (or a fresh Angular 22 fallback): Prettier, Husky, ESLint, lint-staged, a shared style guide, per-agent instruction files, and MCP servers – a codebase that is safe and productive to work on together with AI coding agents.

Angular v22 Package manager pnpm 10 Node 22.22+/24.15+/26 (target 26) Est. time 45–60 min Level intermediate

About this lab

"Agentic engineering" means treating AI coding agents (Claude Code, Codex, Gemini, Junie, Copilot, Cursor, Cline, Windsurf, …) as first-class teammates. An agent with no guardrails produces inconsistent "AI slop"; an agent given a precise style guide, an auto-fixing linter, a pre-commit hook and secret-deny rules becomes a reliable contributor. Each step has a Goal, a task, a collapsible Solution and a Checkpoint – try first, then peek. You cloned this repository in Lab 00; when a solution says "copy the full file from this repo", grab it from your local clone. From Step 6 onward, let your AI agent do the typing.

Required path and optional extensions

Use one agent, the Angular MCP, AGENTS.md, the relevant style guides and the verification contract. Keep existing working tooling. Steps 2–4 can be demonstrated on the clone when your project already has equivalent checks. In Step 5 start with the index and guides for the files you edit. In Step 6 configure your chosen agent only. In Step 7 connect Angular MCP only.

Additional agents, Figma, Spartan, Chrome automation and companion apps are optional. Finish by showing a loaded instruction path, a successful tool call and verified counter behavior. See the delivery record for evidence to save.

Use checks that exist in your project

The workshop clone already has pnpm workshop:check. In your own project, first map build, lint, formatting and tests to its actual scripts. If they match this workspace, copy scripts/workshop-check.mjs and VERIFICATION.md from the clone and add "workshop:check": "node scripts/workshop-check.mjs" to package.json scripts. Keep the packageManager field consistent with your chosen pnpm version.

If the scripts or test platform differ, run the equivalent commands independently and record them instead of copying the runner unchanged. Missing checks remain explicit. workshop:material is for authors checking this workshop clone; it is not required in a participant project without the labs directory.

Instruction precedence and discovery differ by harness. Inspect the files actually loaded. A written rule guides behavior; a permission setting controls an operation; neither is proof that the requested feature works.

Learning objectives

  • Enforce formatting and linting automatically with Prettier, ESLint, Husky and lint-staged.
  • Author a shared, multi-file style guide that both humans and agents follow.
  • Wire up per-agent instruction files that all point at one source of truth (AGENTS.md).
  • Make one successful Angular MCP call; add other tools only when the chosen task needs them.
  • Validate the setup by having an agent build a feature and checking it follows AGENTS.md and the style guide.

Prerequisites

  • Node.js (22.22+, 24.15+ or 26+) and pnpm (npm i -g pnpm@10.29.3), plus the Angular CLI (pnpm dlx @angular/cli@22.0.0 --version).
  • Git configured (name + email) and at least one AI coding agent installed (e.g. Claude Code or Codex).
  • Your Lab 00 project (or permission to create a fallback), a terminal, and your editor (VS Code / JetBrains).

Steps

  1. Choose or scaffold the Angular project

Goal: work in your Lab 00 project, or create a fresh Angular 22 fallback workspace.

Your task

Open your Lab 00 project. If it isn't a suitable Angular workspace, generate a fallback named my-agentic-app (a distinct name, so it can't collide with the ng-agentic repo you cloned in Lab 00) with pnpm as the package manager, then verify it builds and serves.

2 Clean up the initial commit & format with Prettier

Goal: remove duplicated boilerplate and run Prettier across the whole repo.

Your task

  1. If ng new generated duplicated per-tool instruction files (CLAUDE.md, GEMINI.md, …), keep a single AGENTS.md – Step 6 rebuilds the thin files properly.
  2. Add a format script, a prettier.config.js and a .prettierignore, then run the formatter.
Show solution

package.json → scripts:

json"format": "prettier --write ."

Copy prettier.config.js and .prettierignore from this repo. The essentials: printWidth: 120 (matches the ESLint max-len rule, so the tools never fight), singleQuote: true, the angular parser for *.html, and ignores for .angular/coverage/dist/node_modules.

shellpnpm format   # runs: prettier --write .

Checkpoint: pnpm format completes and re-running it reports no further changes.

3 Husky + ESLint + lint-staged

Goal: lint and format staged files only before every commit – the safety net that keeps agent-generated commits clean even when the agent forgets to format.

Your task

  1. Install Husky and initialize it (pnpm exec husky init).
  2. Add Angular ESLint via the schematic and run a first lint pass.
  3. Install lint-staged, configure per-filetype commands, and point the pre-commit hook at it.
Show solution 
shellpnpm add -D husky
pnpm exec husky init

ng add angular-eslint               # creates eslint.config.js + a lint target
pnpm lint          # runs: ng lint
pnpm lint --fix    # auto-fix where possible

pnpm add -D lint-staged

Add to package.json:

json"lint-staged": {
  "*.{html,js,ts}": ["eslint --fix", "prettier --write"],
  "*.{css,json,md,scss}": ["prettier --write"]
}

Replace the contents of .husky/pre-commit with:

shellpnpm exec lint-staged

Code files get eslint --fix then prettier; non-code files only get Prettier. ESLint fixes logic/style; Prettier owns layout. One caveat: hooks are advisory – anyone can bypass them with --no-verify – so mirror the same checks in CI once your project has a pipeline.

Checkpoint: a .husky/ folder and eslint.config.js exist, and staging a messy .ts file then committing auto-fixes and reformats it.

4 Extend the ESLint configuration

Goal: go beyond the defaults – encode this workspace's stricter Angular, TypeScript and template rules (signals, standalone, OnPush, explicit return types, ordered attributes, control-flow syntax).

Your task

Extend eslint.config.js with three blocks – a global ignores list, a TypeScript block and an HTML template block – then run pnpm lint --fix and fix the few remaining issues by hand, or have your agent do it.

Show solution – eslint.config.js

The shape of the config:

  },
  {

Copy the full file from this repo's eslint.config.js and adjust the selector prefix (this repo uses lxt and ignores labs/ – use app or your own prefix, drop the labs/ ignore).

shellng lint --fix

Two issues typically remain for hand-fixing (or your agent): OnPush change detection on app.ts, and a missing return type in main.server.ts.

Checkpoint: pnpm lint passes (warnings allowed, no errors) after manual fixes.

5 Add the Angular Coding Style Guide

Goal: create a style-guide/ folder – one index plus per-topic files – that both humans and agents read. ESLint can't express everything (naming intent, commit format, a11y expectations); a written guide captures those judgement calls, split so an agent loads only what's relevant.

Your task

Create the style-guide/ folder with these files, then fill the topic files with your team's rules (the "Key rules" column summarizes what each covers in this workspace).

Your task

8 Take it for a spin: validate the setup

Goal: prove the setup works – an agent told only what to build should independently reach for the conventions you encoded, follow AGENTS.md and the style guide without you asking, and sail through pnpm lint and the pre-commit hook.

Your task

  1. Ask your agent to implement a small feature – deliberately don't specify which Angular APIs to use. E.g.: "Create a standalone counter component in src/app/counter/ that shows a count, lets me increment and decrement it, and indicates whether the count is even. Follow the project conventions."
  2. Review the result against the checklist below – does it match AGENTS.md and the style guide?
  3. Run pnpm lint, then stage and commit to confirm the hook formats/fixes automatically.
  4. Anything off-style? Don't just correct it in chat – tighten the relevant ESLint rule or style-guide entry so the lesson sticks. The repo is the prompt.

Behavior check: initial count is 0/even; increment shows 1/odd; decrement restores 0/even; a second decrement shows -1/odd. Both controls work by keyboard. Mark input/output, DI and loop tracking as not exercised if the counter does not need them.

Controlled experiment: in a disposable worktree, generate the counter before and after adding one project-specific naming rule. Use fresh sessions with the same model and prompt. Record the instruction paths loaded, the resulting names and the behavior checks. One run illustrates an effect; repeat before claiming that a rule reliably changes output. Do not add another rule until you know the existing instruction was discovered and the failure is repeatable.

Show solution – what "on-style" output looks like

An inline excerpt of a counter (put the template in its own HTML file in your project) (src/app/counter/counter.ts):

tsimport { ChangeDetectionStrategy, Component, computed, signal } from '@angular/core';

@Component({
  selector: 'app-counter',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <p>Count: {{ count() }} ({{ isEven() ? 'even' : 'odd' }})</p>
    <button type="button" (click)="onIncrement()">Increment</button>
    <button type="button" (click)="onDecrement()">Decrement</button>
  `,
})
export class Counter {
  protected readonly count = signal(0);
  protected readonly isEven = computed(() => this.count() % 2 === 0);
  protected onIncrement(): void {
    this.count.update((value) => value + 1);
  }
  protected onDecrement(): void {
    this.count.update((value) => value - 1);
  }
}

Notice what the agent did without being told: OnPush, signals + computed(), protected readonly, on-prefixed handlers, explicit : void, type="button", the app- prefix. When the agent gets it wrong, treat the miss as a gap in the repo: sharpen a rule, then re-run the experiment.

shellpnpm lint        # no errors
pnpm build       # compiles cleanly

Checkpoint: an agent-generated feature passes pnpm lint, visibly follows AGENTS.md and the style guide, and was auto-formatted by the pre-commit hook on commit.

Definition of Done

You're finished when…

  • ✅ pnpm start serves the app and pnpm build succeeds.
  • ✅ pnpm format and pnpm lint both run clean (warnings OK, no errors).
  • ✅ Committing a messy staged file auto-fixes & reformats it via Husky + lint-staged.
  • ✅ style-guide/ has an index and the relevant topic guides, cross-linked; remaining topics are extensions.
  • ✅ AGENTS.md exists and the chosen agent loads it.
  • ✅ The chosen agent’s permissions were tested with a harmless fixture; the report records what was blocked and any uncovered access paths.
  • ✅ .mcp.json registers the Angular CLI (and other) MCP servers; your agent can use them.
  • ✅ An agent-built feature lands on-style and passes pnpm lint without manual fixups.
