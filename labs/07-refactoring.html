Refactoring a Dusty Angular Component

The payoff lab. Take a real, overgrown Angular component – any everywhere, lifecycle hooks, *ngIf, an 800-line file – and rebuild it into something small, modern, and signal-based. You won't freestyle it: you'll follow a repeatable 7-step blueprint, let the AI do the heavy lifting, and review every change like it came from a junior on your team.

Angular v22 Package manager pnpm 10 Skill ng-refactor Builds on Labs 00–06 Est. time ~30 min Level advanced

About this lab

Over years, components collect features, special cases, and workarounds until UI, state, and business logic blur into one dusty file: high mental load, risky to change – and harder for an AI agent to grasp than for a human. You'll fix that with the ng-refactor skill, which encodes a 7-step blueprint: Analyse → Declutter → Update → Modernize → Type → Refactor → Review. Each step is verified by the same gauntlet (build → lint → format → test) and paused at a clean checkpoint to review and commit before the next. The guided ~30 min run is the booking-summary live path below; the seven steps on a full legacy component – and the playbook in 07-REFACTORING.md – are the advanced continuation after the workshop.

Why this matters

AI makes rewriting fast – which is exactly why it's dangerous without guardrails. A blueprint turns "rewrite this component" (an unreviewable 800-line diff) into small, verifiable moves. AI accelerates the rebuild; the architecture decisions stay human.

Required live path

One complete refactoring cycle in 30 minutes

Use the small booking-summary exercise at /refactoring-lab. Run its six characterization tests, replace synchronized derived state with computed values, rerun checks and review the gain. Allow 30 minutes.

The seven-step legacy-table blueprint below is the advanced continuation. A full workspace update or 936-line component refactor is not required during class. Use the shared verification contract and keep exact baseline diagnostics visible.

Learning objectives

  • Drive a legacy Angular component through a repeatable, verifiable refactoring blueprint.
  • Use the ng-refactor skill, paired with ng-migrate for the official schematics.
  • Replace any, lifecycle hooks, and old patterns with strict types, signals, inject(), control flow, and OnPush.
  • Apply AI guardrails: plan first, small reviewable steps, keep comments & domain logic, prove each step with the gauntlet, review before commit.

Before you begin – pick your target

After the live path, choose one overgrown component to carry through all seven steps:

  • Your own project (from Lab 00) – the primary path: pick a component whose contract and scope fit the available time.
  • This repo – advanced continuation: src/app/components/table/ is a genuinely complex, multi-file feature.
  • The workshop example – another option: a deliberately dusty component at L-X-T/ng-days-refactoring-ai.

A fallback target's first lint or test run will expose existing debt – that's the starting point: record the failures, add a behavior safety net, then start refactoring.

Pre-commit hook vs. red baseline

This workspace's pre-commit hook runs lint-staged (eslint --fix + Prettier) on staged files. While a legacy file still carries lint errors, a checkpoint commit will be partially auto-fixed and then blocked by the remaining errors. Commit early checkpoints with git commit --no-verify, and let the hook take over once the gauntlet is green.

The blueprint – 7 steps

Each step: a Goal, a Your task box, a collapsible Solution with prompts & commands, and a Checkpoint. The agent does most of the typing – you steer and review. Start each step by invoking the skill with the step name and component path.

  1. Analyse – understand it, plan it, record the baseline
  2. Declutter (Entschlacken) – delete what's dead
  3. Update (NG Update) – modern toolbox
  4. Modernize (Modernisieren) – signals, control flow, OnPush
  5. Type (Typisierung) – kill any
  6. Refactor – shrink, split, structure
  7. Review – confirm the gains, then commit

1 Analyse

Goal: understand the component, write a plan, record the baseline, and stand up a safety net.

Refactoring without a plan and without tests is gambling. Read the component with its template, styles, and tests together; name the single responsibility it should have – everything else is a candidate to extract or delete. Then pin its behavior with a test before touching production code.

Your task

  1. Have the agent list the smells: LoC, lifecycle hooks, any/weak types, old patterns (*ngIf, @Input(), ngClass), explicit ChangeDetectionStrategy.Eager (what ng update pins on legacy components), template logic, duplication, unclear names.
  2. Ask for an ordered plan following the blueprint – and clarifying questions before any code change.
  3. Establish a safety net: confirm or add a behavior test, run the gauntlet, and record whether the baseline is green or already red.

Its job is: render a paginated, sortable data table.
List the smells and propose an ordered 7-step plan with the expected win per
step. Ask me clarifying questions first – DO NOT change code.

Pin behavior with an e2e test if coverage is thin (see create-e2e-tests) – this workspace has no Playwright setup yet, so lean on its unit-test baseline; in your own project use its e2e runner if one exists, and set one up only if your time budget allows. Then run each non-mutating baseline check independently so a known-red lint result cannot suppress formatting or test results. If it's red in a fallback target, write down the exact failures first:

shellgit status   # must be clean – the blueprint checkpoints per step

pnpm test --watch=false
Plan first, then implement

Resist letting the agent edit during analysis. End the prompt with "ask me clarifying questions first – don't change code yet." The quality of the spec up front decides everything after.

Checkpoint: a written plan, answered questions, a behavior safety net, and a green or documented-red baseline. No production code changed.

2 Declutter (Entschlacken)

Goal: remove everything dead – pure subtraction, the lowest-risk change there is.

Before you modernize or restructure anything, take out the trash. Smaller surface area means every later step has less to reason about – for you and for the agent.

Your task

Delete dead code, unreachable branches, unused imports/inputs/outputs/fields/methods, commented-out blocks, and redundant SCSS – but keep meaningful comments and domain logic. Verify the gauntlet.

Show solution – declutter prompt 
promptng-refactor step 2 (Declutter) for the same component.
Remove dead code, unused members and imports, and commented-out blocks.
KEEP all meaningful comments and any domain logic. Drop redundant SCSS.
Behavior must not change. Show me the diff.
shellpnpm workshop:check

Checkpoint: only live code remains, behavior unchanged, gauntlet green. "Dead code" is not "code I don't understand" – if a block encodes a domain rule, leave it and ask. The diff is small and obviously safe.

3 Update (NG Update)

Goal: make the modern toolbox available – a workspace-level step, run once, not per component.

You can't migrate to APIs your Angular version doesn't have. Bring Angular and its dependencies up to date so Step 4's schematics exist, and let the version's automatic migrations run. If your own project isn't already on a current Angular, skip this step during the workshop and run it as homework – do steps 1–2 live and continue from step 4 once the update lands.

Your task

Update Angular and the CLI/ESLint packages, review the automatic migrations they apply, and bring other npm packages along – handling security while versions move (CSP, Trusted Types, 3rd-party packages).

Show solution – update commands 
shellpnpm ng:update     # ng update @angular/cli @angular/core angular-eslint @angular-eslint/builder
# or, in an Nx workspace:
nx migrate latest && nx migrate --run-migrations

Review what the automatic migrations changed, then verify:

shellpnpm workshop:check

For cadence and the automatic-migration list, see modern-angular.md.

Cadence

Keep Angular current: at least 2× a year for majors, ideally every couple of months for minors. Staying close to latest makes every future refactoring cheaper.

Checkpoint: Angular is current, automatic migrations applied and reviewed, dependencies updated, and the gauntlet is green.

4 Modernize (Modernisieren)

Goal: adopt modern Angular – official schematics first, then the changes they don't cover.

Prefer Angular's official migration schematics over hand-edits: they rewrite deterministically and update every reference (templates, tests, call sites). Delegate them to the ng-migrate skill, one migration per checkpoint. Then do the manual modernization the schematics can't.

Your task

  1. Run schematics one at a time, verifying after each: standalone, control flow (@if/@for), inject(), signal input()/output()/queries, self-closing tags, ngClass/ngStyle → bindings, lazy routes, unused-import cleanup.
  2. Replace lifecycle hooks: setup into the field initializer / constructor; takeUntilDestroyed() for manual subscriptions; computed() off signal inputs instead of ngOnChanges; effect() / afterNextRender() only to synchronize imperative APIs, in place of ngAfterViewInit. Best of all: no hook.
  3. Delete the explicit ChangeDetectionStrategy.Eager pin so the component gets the v22 default, OnPush (do not write OnPush explicitly); use computed() for derived state. This is a real behavioral change – Eager components are checked on every zone tick, OnPush ones only on signals, inputs, and events – which is why it pairs with the signal migration, not before it.

standalone → control-flow → inject → signal-input → signal-queries →
outputs → self-closing-tag → ngclass-to-class → ngstyle-to-style →

One migration, one checkpoint

Don't let the agent chain ten migrations into one diff. Each schematic gets its own gauntlet and review – that's how you keep a green, bisectable history when something breaks.

Checkpoint: chosen migrations applied (each gauntlet-green and checkpointed), no replaceable lifecycle hooks remain, and the component is OnPush.

5 Type (Typisierung)

Goal: turn types into a safety net – the first real lever in legacy code.

With structure and APIs modern, make the compiler your ally. Replacing fuzzy types with explicit ones surfaces hidden bugs and makes the structural cut in Step 6 safe.

Your task

Replace every any, add explicit return and parameter types, prefer unknown over any and type over interface, and extract small precisely-named types into their own files. Type the inputs and outputs precisely.

Show solution – typing prompt & check 
promptng-refactor step 5 (Type) for this component.
Remove every `any`; add explicit return and parameter types.
Prefer `unknown` over `any` and `type` over `interface`.
Extract non-trivial types into their own files (Rule of One).
Type the inputs/outputs precisely. Don't change behavior.

The linter is the checklist – these must be clean:

shellpnpm lint   # no @typescript-eslint/no-explicit-any, explicit-function-return-type

Checkpoint: no any remains, no-explicit-any and explicit-function-return-type are clean, and the gauntlet is green. Before/after example and rules: clean-code-and-structure.md.

6 Refactor

Goal: the real structural work – small functions, clear ownership, readable top-to-bottom.

With dead code gone, APIs modern, and types tight, the structural changes are now safe and obvious. Work in small, reviewable diffs – and make every change earn its keep.

Your task

  • Shrink functions. Split big handlers (validation + mapping + state + UI side effects) into small, intent-revealing functions (buildRequest, validateInput, updateSelection).
  • DRY. Lift shared logic into services, directives, pipes, utils, or sub-components.
  • SRP & Rule of One. Split an oversized component into smaller focused ones, each its own file, each ≤ ~400 LoC.
  • Structure. Reorder members to the canonical order; thin the template (logic → computed()/methods, complexity ≤ 10); prefer private, readonly, const.
Show solution – refactor prompt & member order 
promptng-refactor step 6 (Refactor). One concern at a time, show each diff:
1) describe the flow of the big handler, then split it into named functions;
2) extract shared logic into a service/util;
3) if the file is > ~400 LoC, split into focused sub-components;
4) reorder members to the canonical order and thin the template.
Every change must reduce complexity, clarify responsibility, or modernize.

Canonical member order (full details in clean-code-and-structure.md):

decorator (@Component) class (extends & implements) members ├─ injects → input → model → output → queries → signals → other methods └─ static → constructor → other methods

Checkpoint: each unit has one responsibility, no file exceeds ~400 LoC, functions are small and named, the template is logic-light, and every diff was gauntlet-green and checkpointed. Tip: the agent extracts best when you make it describe the flow first, then slice it into named functions.

7 Review

Goal: confirm the gains, write down the why, and hand the result to a human – you.

Read the finished component top-to-bottom as if onboarding fresh. The agent's work is treated like a junior's: you review and commit every change.

Your task

Walk the review checklist, summarize what changed and why (the benefit per change), note follow-ups, and only then commit. For a large scope, run a deeper architectural pass.

Show solution – review checklist
  • Reads top-to-bottom; one clear responsibility; canonical member order.
  • No any; small named functions; no file > ~400 LoC; OnPush; no unexplained lifecycle or synchronization logic.
  • Comments and domain logic intact; tests green and still meaningful (behavior, not internals).
  • Every change delivered a real gain – less complexity, clearer responsibility, or modern.

The general review practice lives in 04-REVIEWING.md (Lab 04); run the code-review skill for an independent reviewer, or ng-review-architecture for a deeper pass. Then commit through your Git GUI, reviewing the diff one last time.

The human commits

The skill never stages or commits for you. Review the diff, then commit it yourself – the final guardrail that keeps AI a contributor, not an unchecked author.

Checkpoint: you've reviewed the full diff, the gauntlet is green, the gains are written down, and you committed the change yourself.

Definition of Done

You've completed Lab 07 when…

  • ✅ Live path: the six booking-summary tests still pass, the synchronization effect is gone in favour of derived state, targeted lint is clean, full diagnostics match the recorded baseline, keyboard evidence is recorded, and a human reviewed the diff.

Advanced completion – your own component is refactored when…

  • ✅ You drove it through all seven steps, each gauntlet-green and checkpointed.
  • ✅ No any, no replaceable lifecycle hooks, no *ngIf/@Input()/ngClass – strict types, signals, inject(), control flow, OnPush instead.
  • ✅ Functions are small and named; no file exceeds ~400 LoC; the template is logic-light.
  • ✅ Comments and domain logic intact; behavior unchanged and still covered by tests.
  • ✅ You reviewed every change and committed it yourself, with a note on the gains.
  • ✅ Bonus (workspace fallback): restore zoneless change detection (drop zone.js and provideZoneChangeDetection()) and tighten the relaxed budgets in angular.json back towards Angular defaults.
